dsh-cabinet

多模型在同一会话里议政、分工、质检、交付——一条时间轴就是证据

dsh-cabinet 是 DeepSeek Harness 的一个插件：在同一条对话里让多个模型（最多 8 席）轮流发言、争论、出方案，然后按契约把模块并行派给不同模型独立开发，最后自动质检、收口交付。

从安装到跑完第一场：三步、三分钟。下面这张时间轴用本机真实会话日志机械生成——它不是插画，是证据。

三步上手

  1. 设置 → 插件 → 安装本地目录，选 dsh-cabinet 目录。装完应看到插件列表出现「内阁」条目，设置页多出「内阁」面板。

    列表没出现？确认目录指向含 package.json 的那一层（里面还有 cordis.patch.yml 与 index.js），不是上一层文件夹。

  2. 设置 → 内阁，填人数（1–8），每人选 provider 和 model，「擅长」栏写一句它会做的事。保存后 $DSH_HOME/cabinet/seats.json 里应能看到席位配置。

    别手工编辑 seats.json——用记事本保存成带 BOM 的 UTF-8 会让席位被读成 0 个。用设置页面改。

  3. 回到对话，说「开个内阁讨论一下：你的议题」。首辅开题后把话筒交给阁员；判据：换人时出现 model changed 分隔线，每条回复旁挂着各自的模型名。

    席位指到没登录的 provider 会导致整条回合静默失败（对话卡住不动）。用当前对话正在用的那个 provider。阁员忘了交话筒时，说「继续」收回首辅。

七阶段表：一场内阁的骨架

下面这张表是读者最想抄的——每一行告诉你谁做、产出什么、怎么判断这一阶段真的跑通了。

阶段 谁做 工具 产物 怎么判合格
① 召集 首辅 cabinet_convene 议题上桌，席位就绪 对话里出现 cabinet_convene 调用行；GET /api/cabinet/state 里 seats 数组非空、人数与你设置的一致
② 交锋 阁员（三席轮流） cabinet_pass 每位阁员至少说一段，观点充分碰撞 至少一轮 cabinet_pass 完成；每条回复旁挂着不同的模型名；会话日志里有 HDR "change" 行证明换人真的发生了
③ 出方案 首辅 cabinet_propose 2–3 个可选方案，各有优劣 cabinet_propose 返回的 options 数组 length ≥ 2，每个含 title / summary / pros / cons
④ 定分工 用户 + 首辅 cabinet_decide
cabinet_frame		 用户选定方案；首辅出模块契约 cabinet_frame 静态检查 5 项全过：写域不重叠、依赖出口存在、导出路径在己方写域内、依赖图无环、入口唯一
⑤ 并行 首辅 cabinet_dispatch 每个模块一个独立子会话，≤3 并发 cabinet_dispatch 打印的批次数 ≤ 3，每批有不同的 childId；不合格模块自动给 2 轮返工机会，超了就停下来问人
⑥ 拼接审计 质检员（未参与该模块的模型） cabinet_audit 结构化审计结论 每位质检员出 ok 或 ng，附文件行号证据——结论来自真实代码，不是凭感觉
⑦ 交付 首辅 cabinet_integrate delivered 状态 + 文件清单 落 delivered，附实测验证命令与结果——例如 pad(5)==='05'、fmt(9,5)==='09:05'，能直接跑、能复现

共 11 个工具，上面只列了 7 个核心骨架；还有 cabinet_status / cabinet_close / cabinet_yield（cabinet_pass 的兼容壳）。设置页最多 8 席，并行上限 3 并发，单模块返工上限 2 轮。
